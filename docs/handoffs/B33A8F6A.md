# B33A8F6A: Absturz beim Hintergrund-Refresh (Build 31) und Feedback „Button passiert nichts“

Stand 26.11.2026.

## Ursache

- Meldung „Im Hintergrund“, 23.10. 07:46, Version 0.1.0 (31), Role „Non UI“, `EXC_BREAKPOINT`.
- **Abgestürzt ist Thread 5:** `_dispatch_assert_queue_fail` → `dispatch_assert_queue` → `_swift_task_checkIsolatedSwift` →
  `swift_task_isCurrentExecutorWithFlagsImpl` → `closure #1 in AutomationRuntime.start()` → BGTask-Thunk →
  `-[BGTaskScheduler _runTask:registration:]`.
- Thread 0 (`_queue_ensureExistenceOfKnownSceneSessionMap`, `NSData` liest eine Datei) ist **nicht** abgestürzt; das ist der
  gewöhnliche Szenenaufbau von UIKit beim Start, der zur selben Zeit lief. Kein Hinweis auf Dateischutz oder Widget.
- Code in Build 31 (Commit `54c93aa`, `Sources/Location/AutomationRuntime.swift:74`): `BGTaskScheduler.register(..., using: nil)`
  direkt in `start()` einer `@MainActor`-Klasse. Die Closure erbte die MainActor-Isolation; BackgroundTasks ruft sie auf einer
  Hintergrund-Queue auf, die Swift-6-Laufzeitprüfung trapt.
- Build 26 („Nichts gemacht“, 21.10.) hat dieselbe Signatur.

## Stand der übrigen Meldungen

App Store Connect listet am 26.11. sechs Crash-Meldungen, alle aus Build 31 oder älter. Der Fix `7af7a4d` (23.10., `nonisolated`
Registrierung, siehe C1) ist ab Build 32 enthalten; aus Build 32 bis 62 liegt keine Meldung vor. Die Liste enthält nur von
Testern gesendete Meldungen, sie belegt also nicht, dass es keinen Absturz gab.

## Test (neu; C1 hatte den Absturz selbst nicht nachgestellt)

- `Tests/iOSUI/BackgroundLaunchTests.swift` mit Debug-Hilfe `Sources/iOS/BackgroundLaunchSimulation.swift` (nur `#if DEBUG`):
  fängt die Handler ab, die die App wirklich registriert, und ruft sie auf einer Hintergrund-Queue mit einem
  `BGAppRefreshTask` auf. Erwartet `setTaskCompleted` und eine weiterlaufende App. Kein Backend nötig.
- **Rot** (nur `nonisolated` an `registerRefreshTask` entfernt): `testAutomationRefreshLaunchHandlerRunsOffTheMainThread`
  schlägt fehl, App abgestürzt (`EXC_BREAKPOINT`) mit denselben Frames wie Build 31
  (`_dispatch_assert_queue_fail` … `closure #1 in static AutomationRuntime.registerRefreshTask()`).
  Der Fokus-Test bleibt grün (dieser Handler war nie MainActor-isoliert).
- **Grün** (Stand `main`): 2 von 2.
- Grenze: Simulator, App im Vordergrund gestartet; nachgestellt ist der Aufruf des Handlers abseits des Main Threads, nicht der
  Start durch iOS selbst. Gerät ungeprüft.

## Feedback „Button passiert nichts“ (20.10.)

- Zwei Screenshots, Tab „Zeit“, Monatsansicht; eingekreist ist der Toolbar-Knopf zwischen „Heute“ und „+“: **„Zeitraum wählen“**
  (`calendar.range`). Die Auswahlleiste „Zeitraum: 20. Okt.“ ist schon offen.
- Wahrscheinlichste Erklärung (aus Code und Bild abgeleitet, nicht auf dem Gerät nachgestellt): Bei offener Auswahl ruft der
  Knopf `CalendarStore.beginRange(at: focus.day)` erneut auf; derselbe Starttag wird gesetzt, sichtbar ändert sich nichts.
- Seit `3194695` (20.10., Toolbar war abgeschnitten) liegt die Aktion im Mehr-Menü. Der Eintrag ist auch bei offener Auswahl
  noch aktiv; dort wäre er weiterhin ohne sichtbare Wirkung, solange noch kein zweiter Tag gewählt ist (mit zweitem Tag setzt er
  die Auswahl zurück). **Nicht geändert** (nicht Teil des Auftrags); Vorschlag: Eintrag während der Auswahl deaktivieren.
