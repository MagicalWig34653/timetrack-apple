# Handoff F4: Live Activity nach Fokus-Filter

Branch `f4-focus-live-activity`, 18.10.2026. Nicht gemergt, nicht gepusht, Build-Nummer unverändert, kein TestFlight-Upload.
Anlass: Auf dem Gerät (Build 5) startet der Fokus-Filter den Timer verlässlich, aber die Live Activity fehlt.

## Ursachen

Bestätigt (im Code nachgewiesen):
1. **Start der Live Activity nur über `Activity.request`, Fehler verschluckt.** `TimerLiveActivity.sync` rief `try? Activity.request(...)`. iOS erlaubt das nur bei sichtbarer App. Der Fokus-Filter läuft im App-Prozess, aber im Hintergrund (Hintergrundstart oder kurzes Zeitbudget); die Anfrage schlägt dort fehl, ohne Spur. Nichts holte sie später nach.
2. **Kein Nachholen beim Öffnen.** Die Synchronisierung hing nur an `widgetSync` (Änderung von Signatur/`lastLoaded`) und damit an einem Neuladen der Heute-Ansicht. Bei Hintergrundstart durch den Fokus lief `widgetSync` im Hintergrund (Anfrage verweigert); beim späteren Öffnen kam die Aktivierung nur über die Heute-Ansicht. War eine andere Seite offen (z. B. Fokus-Seite), wurde nie neu geprüft.
3. **Warteschlange aktualisierte nichts.** `retryPending` (Start der App, Vordergrund, BGAppRefresh, Knopf) stellte Start/Stopp zu, veröffentlichte aber nie den Zustand. Ein offline gemeldeter Fokus-Start oder -Stopp ließ Live Activity und Widgets bis zum nächsten Neuladen falsch.
4. **Fehlgeschlagene Leseanfrage = „kein Timer“.** `WidgetPublisher.refresh` machte aus einem Netzfehler bei `GET /time/timer` ein „läuft nicht“ und beendete dadurch die Live Activity (und überschrieb den Widget-Zustand). Betrifft Fokus-, Intent- und Wiederholungspfad.
5. **Parallele Abgleiche.** Modell-Sync, Fokus und Vordergrund konnten gleichzeitig „keine Activity“ sehen und mehrere anlegen.
6. **Neuer Timer = Beenden + Neuanfrage.** Im Hintergrund wäre die alte Activity beendet und die neue verweigert worden; Aktualisieren (`update`) ist dagegen im Hintergrund erlaubt.

Vermutet (nicht überprüfbar ohne Gerät):
- Ob der Filter-Callback tatsächlich als „nicht sichtbar“ gilt (wahrscheinlich ja bei gesperrtem Gerät/Hintergrund; bei geöffnetem Gerät und Vordergrund-App könnte die Anfrage durchgehen). Die Seite zeigt jetzt den Systemfehler.
- iOS beendet Live Activities nach 8 h (plus bis 4 h auf dem Sperrbildschirm); der Abgleich beim Öffnen startet sie dann mit dem ursprünglichen Startzeitpunkt neu.

## Umsetzung

- `TimetrackCore/Widget/LiveActivityReconciler.swift` (rein, getestet): `LiveActivityReconciler.plan(desired:existing:)` → behalten/aktualisieren/beenden/starten. Timer läuft ⇒ genau eine Activity mit passendem Startzeitpunkt (vorhandene wird per `update` umgesetzt, Duplikate beendet), kein Timer ⇒ keine. Idempotent. `SerialGate` (Async-Sperre), `LiveActivityOutcome` + `LiveActivityOutcomeStore` (letztes Ergebnis in der App Group, deutsche Kurzfassung).
- `Sources/WidgetShared/TimerLiveActivity.swift`: führt den Plan unter der Sperre aus, nur lebende Activities (`active`/`stale`), schreibt das Ergebnis (`started`, `startDeferred` mit Systemfehler, `disabled`, …). Neu: `reconcileFromSnapshot()` (ohne Netz, aus dem Widget-Snapshot).
- `TimetrackIOSApp`: bei `scenePhase == .active` immer `reconcileFromSnapshot()` (unabhängig von der geöffneten Seite).
- `FocusEnvironment.retryPending`: nach zugestellten Aktionen `WidgetPublisher.refresh` (4 s Budget): beendet/aktualisiert auch im Hintergrund; ein Start wird beim Öffnen nachgeholt.
- `WidgetPublisher.refresh`: Lesefehler veröffentlicht nichts mehr.
- Fokus-Seite: Zeile „Live Activity: …“ im Bereich „Letzte Meldung“ und in „Diagnose teilen“.

Ablauf Fokus-Start im Hintergrund: Timer startet → Snapshot geschrieben → Anfrage verweigert (`startDeferred`) → App öffnen → Abgleich aus Snapshot → Activity erscheint (bei Erfolg `started`, Quelle `foreground`). Fokus-Stopp im Hintergrund: Activity wird beendet (kein Request nötig).

## Push-to-Start (nur Vorschlag, nicht umgesetzt)
Aus dem Hintergrund oder bei beendeter App kann eine Live Activity nur per Push gestartet werden (iOS 17.2+: `Activity<…>.pushToStartTokenUpdates`, `pushType: .token`). Im Backend gibt es dafür nichts: Weder Vertrag noch ADR-0015 (Nachtrag A7: „Live Activity ohne Push-Updates … erst beim nächsten App-Start“) kennen APNs. Nötig wären: Token-Registrierung (Gerät, Push-to-Start-Token, Activity-Update-Token), APNs-Zugang (Schlüssel, Topic `…push-type.liveactivity`), Versand bei Timer-Start/-Stopp, Datenschutz-/Vertragsänderung, Entitlement `aps-environment`. Eigenes Paket mit Backend-ADR; Nutzen: Activity auch bei Start im Web/auf anderer Plattform. Offene Entscheidung für den Nutzer.
