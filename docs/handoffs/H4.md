# H4 – Timer stoppt beim Zurückgehen auf Heute, „Fortführen“

Branch `h4-continue-timer` (Worktree `timetrack-apple-wt/h4`) auf main Build 33. Nicht gemergt, nicht gepusht, Build-Nummer unverändert, kein Upload.

## 1. Fehler „Timer stoppt beim Zurückgehen auf Heute“
**Im Simulator nicht reproduzierbar** (UI-Test `RunningTimerSurvivesNavigationTests` läuft Tabs, Jetzt-Sheet von Heute und anderem Tab per Fertig/Wischen, Zeit-Tagesdetails, Einstellungen push/pop, Hintergrund/Vordergrund und Pull-to-Refresh ab: grün). Ursache per Code-Analyse und Kerntest **reproduziert**: Jede Rückkehr zu Heute startet `TodayStore.load()` (`.task`, `scenePhase`, `revalidate`). Dessen Antwort wurde ohne Prüfung übernommen. Wurde sie vom Server **vor** einer eigenen Start-/Stopp-/Korrekturaktion gelesen und kam danach an (langsames Netz, Start gerade gedrückt, Antwort überholt), überschrieb sie `running` mit dem Zustand davor: ein gerade gestarteter Timer wirkte „gestoppt“ (Leiste zeigt wieder Start), bis zum nächsten Laden. Das passt zu „Zurückgehen auf Heute“, weil dort der Reload läuft.
Fix: `TodayStore.actionEpoch` zählt Beginn und Ende jeder eigenen Aktion (start, stop, correctRunning, continueLast, Warteschlange leeren); `load` verwirft Antworten, wenn sich der Zähler währenddessen geändert hat (die Aktion lädt ohnehin selbst neu). Tests `RunningTimerRaceTests` (4; Stale-Reload nach Start, nach Stopp, Reload während Start, normaler Reload übernimmt weiter Serveränderungen) waren vor dem Fix rot. **Ehrlich:** ob dies die vom Nutzer beobachtete Ursache ist, ist nicht am Gerät bestätigt. Andere Auslöser (z. B. Stopp durch Standortautomatik `departure`, Fokus-Filter, Live-Activity-Knopf) wurden gelesen: sie stoppen nur mit eigener Aktion, nie durch Navigation. Falls es weiter auftritt: Zeit, Bildschirm und ob die Leiste „Start“ oder die Uhr zeigt notieren; Server-Zeitachse (Revision „Timer stopped“ vs. Quelle) zeigt, wer gestoppt hat.

## 2. Letzten Timerblock fortführen
- Angebot nur im Leerlauf und wenn heute ein beendeter Eintrag (Arbeit/Fahrt/Schule) existiert: Heute (Knopf unter der Uhrkarte, iPhone und iPad), Jetzt-Sheet (unter „Weiter/Starten“), Leisten-Kontextmenü (langes Drücken im Leerlauf). Text „Fortführen: Arbeit, zuletzt bis 10:03“. Mac nicht umgesetzt.
- Server (Vertrag 0.27.0, Backend `docs/handoffs/W2-reopen.md`): `PATCH /time/segments/{id}` mit `endedAt: null`, Grund „Timer fortgesetzt“, `If-Match`. `SegmentCorrection.reopen` sendet das explizite `null`.
- **Lücke zählt als Arbeitszeit** (Servervorgabe): Unter dem Knopf steht „Lücke von 25 Min wird als Arbeitszeit gezählt“ (ab 1 Min; bei Fahrt/Schule „zum Eintrag gezählt“). Bei Lücke > 15 Min fragt ein Dialog „Fortführen (Lücke zählt mit)“ oder „Neu starten (Lücke bleibt Pause)“; im Leisten-Kontextmenü stehen beide Einträge direkt. Neu starten = neuer Eintrag gleicher Art/Ort/Notiz ab jetzt.
- **Fallback** (Server ohne 0.27.0, z. B. vor Deploy): lehnt der Server mit 4xx ab (400/404/405/409/412/422) oder antwortet mit weiterhin beendetem Eintrag, startet die App einen neuen Eintrag derselben Art/Ort (Notiz wird übernommen); Hinweis „Neuer Eintrag ab jetzt, die Lücke bleibt eine Pause. Der Server kann Einträge nicht wieder öffnen.“ Erfolgsfall: „Eintrag wieder geöffnet, die Lücke zählt mit.“ Netzfehler/5xx/429/401 werden nicht zum Fallback.
- **Offline**: `TimerActionQueue` hat `QueuedTimerAction.Command.resume(ContinueTarget)` (Reopen mit Fallback bei Auslieferung; Auslieferung hat dann keine Rückdatierung auf den Tastendruck); „Neu starten“ offline = gewöhnlicher `.start`. Anzeige sofort laufend (`TodayDisplay`, Widget-Snapshot), Hinweis „Wird gesendet, sobald der Server erreichbar ist.“
- Glossar: „Fortführen“ (`docs/glossary-ui.md`), abgegrenzt von „Weiter“ (immer neuer Eintrag).
